### Finding 1 — P2: `--exclude=scripts` hides `run_onchange_` drift, but the hiding is intentional and partially correct

**Is it hiding real issues?**

`run_onchange_` scripts are re-run by chezmoi whenever their content or their template inputs change. `chezmoi verify` reports them as "failed" (exit 1) if the script has never been run, or if it has been run but chezmoi has no record of when — which is always the case for `run_onchange_` scripts, because chezmoi tracks their last-run hash in `~/.config/chezmoi/chezmoistate.boltdb`, not in the working tree. On a fresh machine or after a re-install, `verify` would flag them even if they should not be re-run.

So yes, `--exclude=scripts` does suppress real information: if a `run_onchange_` script's content has changed since it was last run, `verify` without the flag would catch that. With the flag, that drift is invisible.

**Is this expected behavior for `run_onchange_`?**

Partially. `chezmoi verify` for scripts checks whether the script's run-state in `chezmoistate.boltdb` matches the current hash. If the script changed, `verify` exits non-zero even with `--exclude=scripts`... wait, no — `--exclude=scripts` removes scripts from consideration entirely, so changed scripts will never fail verify regardless. That is the real gap.

### Finding 3 — P2: No distinction between "script never run" and "script content changed"

The reason `--exclude=scripts` was likely added is that `chezmoi verify` exits 1 for scripts that are pending execution (i.e., their hash has changed but they haven't been re-run yet). That is a valid false-positive suppression on a fully-applied machine. But the current approach throws away all script signal.

A better approach is to check `chezmoi state list scripts` to distinguish:
- Scripts with no state entry at all (never run — probably a real gap on a new machine, acceptable to suppress).
- Scripts whose stored hash differs from the current rendered hash (content changed since last run — this is real drift that should surface).

chezmoi does not expose a single command for this, but `chezmoi diff` with no `--exclude` will show scripts with pending changes as a diff entry. The validator currently does not call `chezmoi diff` at all.

### Finding 4 — P2: `--include=files` is strictly better than `--exclude=scripts` for the stated intent

`--exclude=scripts` excludes scripts but still includes `symlinks`, `dirs`, `externals`, and `templates`. `--include=files` is more precise: it verifies only regular managed files, which is exactly what the validator's docstring implies it wants to check ("verify managed files are in sync"). The difference matters if chezmoi ever gains new entry types.

The chezmoi docs distinguish these flags: `--include` is a positive allowlist, `--exclude` is a negative blocklist applied after the default set. Using `--include=files` makes the intent unambiguous and avoids including future entry types by accident.

### Recommendations

**P1 — Script drift is invisible. Add a separate check that surfaces it without causing false positives:**

```python

["chezmoi", "verify", "--include=files"]

# Add a second call for scripts using diff to detect content changes:
proc = subprocess.run(
    ["chezmoi", "diff", "--include=scripts"],
    capture_output=True, text=True, timeout=30,
)
if proc.stdout.strip():  # non-empty diff means scripts have changed content
    result.add(
        path="chezmoi",
        message="chezmoi scripts have pending changes (run chezmoi apply to execute)",
        severity=Severity.WARNING,   # warning, not error — pending re-run is expected
        rule="chezmoi.script-drift",
    )
```

Using `chezmoi diff --include=scripts` tells you whether any script's rendered content has changed since last applied, without triggering false positives for scripts that have already been run at their current hash.

**P2 — Replace `--exclude=scripts` with `--include=files`** in both `chezmoi.py` line 38 and `test_chezmoi.py` line 17. Same behavior today, but correct semantics and future-proof.

**P3 — Fix the test assertion message** to include stdout:

