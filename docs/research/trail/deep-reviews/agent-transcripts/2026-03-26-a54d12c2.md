## Root Cause Analysis

**The bug has two interacting causes:**

### Cause 1: Stale global lockfile (PRIMARY)

The global mise lockfile at `~/.config/mise/mise.lock` pins specific versions for tools declared as `"latest"` in `~/.config/mise/config.toml`. When `mise upgrade --yes` upgrades a tool (e.g., atuin 18.13.4 -> 18.13.5), it installs the new version and removes the old one. However, the subsequent `mise lock` call (line 91 of the old code) only updates the **project-level** lockfile -- it does NOT pass `--global`, so the global lockfile retains stale version pins (the lockfile even had atuin pinned to v18.13.**3**, two versions behind).

When `mise install --yes` runs next, it resolves `latest` using the stale global lockfile, which points to the OLD version. It reinstalls the old version. Then `mise prune --yes` removes these stale reinstallations.

Evidence from `mise ls`:
- atuin@18.13.4 shown as "active" (linked to config.toml) despite 18.13.5 being installed
- `mise which atuin` returns the 18.13.4 path
- The lockfile pins atuin to v18.13.3 download URLs

### Cause 2: Wrong step ordering (SECONDARY)

The old order was: upgrade -> lock -> reshim -> install -> prune. This means:
- `install` runs before `prune`, reinstalling old versions that prune immediately removes
- Wasted bandwidth and time downloading/installing tools that get pruned seconds later

## Fix Applied

**File:** `/Users/rmanaloto/dev/github/ray-manaloto/macos-development-environment/src/mde/maintain/update.py`

Three changes:

1. **`_run_mise_lock()` now runs `mise lock --global`** in addition to the project-level lock, ensuring the global lockfile's "latest" resolution reflects the versions that `mise upgrade` just installed.

2. **Reordered steps:** prune now runs BEFORE install (upgrade -> lock --global -> prune -> install -> reshim). This cleans up orphan old versions before installing, so `mise install` never wastes time reinstalling stale versions that would get pruned.

3. **Added `mise doctor` post-cycle health check** to catch any tools that went missing after the full cycle, failing the update if issues are detected.

### Lockfile platform bloat note

The lockfile targets 6 platforms (linux-arm64, linux-arm64-musl, linux-x64, linux-x64-musl, macos-arm64, windows-x64) despite this being a macOS arm64-only machine. The `mise lock --platform macos-arm64` flag could limit this, but it would break portability if the config is shared across machines. This is a minor performance concern, not a correctness issue -- I left it as-is since the config is managed by chezmoi (which implies multi-machine intent).
