### Issues

**Important (should fix):**

1. **Missing test for partial fnox-get failures.** The implementation correctly logs a warning and skips keys where `fnox get` fails (line 46 of `export_to_doppler.py`), but no test exercises this branch. A key that fails `fnox get` should be skipped while the remaining keys still upload. Add a test where one of the `fnox get` calls returns `returncode=1` to verify the function still exports the other secrets and returns 0.

2. **Missing dry-run / confirmation for a destructive one-time migration.** This is a one-time bulk upload of ~40 secrets to a cloud service. There is no `--dry-run` flag, no confirmation prompt, and no summary of what will be uploaded before it happens. For a migration tool, this is a meaningful safety gap. At minimum, consider logging the list of key names (not values) that will be exported and requiring a `--confirm` flag or printing a count before proceeding. This was not in the plan but is a justified addition.

3. **No check for `is_doppler_available()` before calling `doppler_set_secrets()`.** The existing `doppler.py` module provides `is_doppler_available()`, but `export_fnox_to_doppler()` does not call it. If Doppler is not installed, the error will come as a cryptic `FileNotFoundError` from `subprocess.run` rather than a clear diagnostic message. Add a guard at the top of the function.

**Suggestions (nice to have):**

4. **The `fnox list` parsing uses string splitting which is fragile.** The parser relies on `line.split()[0]` to extract the key name from fnox output. If fnox ever changes its output format (e.g., adds a header line, changes column spacing), this will silently pick up wrong data. Consider adding a comment documenting the expected format, or at minimum a guard that checks the extracted key looks like a valid environment variable name (e.g., matches `^[A-Z_][A-Z0-9_]*$`).

5. **Tests import `export_fnox_to_doppler` inside the `with` block.** In `TestExportFnoxToDoppler`, the import of `export_fnox_to_doppler` is done inside the `with patch(...)` context manager. This works because the module is already imported at that point (Python caches imports), but it reads oddly. A top-level import at the test file level would be cleaner and more consistent with how the `doppler.py` functions are imported at the top.

6. **`doppler_set_secrets` can return non-zero even when some secrets succeeded.** The current flow does a single bulk upload. If Doppler rejects one malformed key, the entire batch fails. For a migration of 40 secrets, consider chunking or at least documenting this all-or-nothing behavior.
