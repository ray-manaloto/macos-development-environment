## Summary

I've researched the official Claude Code hooks documentation thoroughly. Here are the answers to your questions:

### 1. Hook Scoping: Are hooks project-local vs global?

Hooks **are NOT project-local by default**. They are **scope-based** and apply hierarchically across ALL projects once configured. Hooks can be defined in multiple scopes:

| Location | Scope | Applies to |
|----------|-------|-----------|
| `~/.claude/settings.json` | **User (global)** | ALL projects on your machine |
| `.claude/settings.json` | **Project** | Only this project (shareable via git) |
| `.claude/settings.local.json` | **Local** | Only this project, only for you (gitignored) |
| Plugin `hooks/hooks.json` | When plugin enabled | When plugin is active |
| Skill/agent frontmatter | While active | While the skill or agent is running |

**Critical Finding**: A hook defined in `~/.claude/settings.json` (user scope) **runs in ALL projects** without exception.

### 2. Settings File Hierarchy

The precedence order for overlapping settings is strict (from highest to lowest priority):

1. **Managed** (highest) - Cannot be overridden
2. **Command-line arguments** - Temporary session overrides
3. **Local** (`.claude/settings.local.json`) - Overrides project and user settings
4. **Project** (`.claude/settings.json`) - Overrides user settings
5. **User** (`~/.claude/settings.json`) (lowest)

**Important**: `.claude/settings.local.json` overrides both project and user settings for the same project. More specific scopes always win.

### 3. Do PreToolUse hooks from one project leak into another?

**Yes, absolutely.** If a PreToolUse hook is defined in your global user settings (`~/.claude/settings.json`), it fires in **every project** where you use Claude Code.

From the documentation:
> "When the same setting is configured in multiple scopes, more specific scopes take precedence"

But there is **no project-isolation mechanism**. Global hooks are truly global. This is the root cause of your problem.

### 4. Is there a way to scope hooks to only run in a specific project directory?

**Not directly through the hook configuration itself.** However, you have these workarounds:

**Option A: Conditional logic in the hook script**
Your hook script can check the `cwd` (working directory) from the hook's JSON input and exit early if it's not the intended project:

```bash
#!/bin/bash
INPUT=$(cat)
PROJECT_DIR=$(echo "$INPUT" | jq -r '.cwd')

# Only run in the MDE project
if [[ "$PROJECT_DIR" != *"macos-development-environment"* ]]; then
  exit 0  # Do nothing outside MDE
fi

# Your actual hook logic here
```

**Option B: Use project-local settings instead of user settings**
Define the hook in `.claude/settings.local.json` (project-local scope) rather than `~/.claude/settings.json`:
- It only runs in that specific project
- It's gitignored, so it's not shared
- Lower precedence than project settings, but higher than user settings

**Option C: Matcher-based filtering**
Use the `matcher` field to restrict when the hook runs (but this filters by tool name, not project):

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [...]
      }
    ]
  }
}
```

### 5. What happens when a hook command fails (like when a binary doesn't exist)?

Hook error handling is clearly documented:

**Exit Codes**:
- **Exit 0**: Success. Hook proceeds (or JSON output is parsed for decisions)
- **Exit 2**: Blocking error. The action is blocked and the error message (from stderr) is fed back to Claude as feedback
- **Any other exit code**: Non-blocking error. The action proceeds. Error message is logged but NOT shown to Claude

**Your Specific Problem**:
When `uv run mde-py hooks guard-dotfile-edit` fails (command not found in non-MDE projects):
- The PreToolUse hook exits with non-zero (probably exit code 1 or 127)
- Since it's not exit 0 or exit 2, **the action should technically proceed**
- But if the script is written to exit with exit 2 on error, it will **block ALL bash commands** in those projects

**From the docs**:
> "Your script tells Claude Code what to do next by writing to stdout or stderr and exiting with a specific code."
