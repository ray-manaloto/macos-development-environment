## P1 CRITICAL

### 1. Shell injection via `TOOL_INPUT_COMMAND` expansion in hooks.json (both plugins)

**Files:** `chezmoi-toolkit/hooks/hooks.json` line 9, `mise-toolkit/hooks/hooks.json` line 9

**Both hooks.json files contain:**
```json
"command": "bash ${CLAUDE_PLUGIN_ROOT}/hooks/scripts/guard-install.sh \"${TOOL_INPUT_COMMAND}\""
```

`${TOOL_INPUT_COMMAND}` is interpolated directly into a shell command string before the shell processes it. The double-quoting (`\"${TOOL_INPUT_COMMAND}\"`) in the JSON value is passed to the shell as a literal string — but the shell that evaluates the `command` field will still interpret `$()`, backticks, and other shell metacharacters embedded within `TOOL_INPUT_COMMAND` before they reach the script as `$1`.

Concrete attack: if `TOOL_INPUT_COMMAND` is `$(rm -rf ~/important)`, the hooks.json command string becomes:
```bash
bash .../guard-install.sh "$(rm -rf ~/important)"
```
The outer shell evaluating that `command` string expands `$(rm -rf ~/important)` before even invoking `guard-install.sh`. The script never receives the value — the subshell runs first.

Whether this actually fires depends on whether Claude Code evaluates hooks.json `command` via `bash -c` (where variable substitution occurs at evaluation time) or passes it to `exec` directly. If it is `bash -c "..."`, the embedded subshell executes with the privileges of the Claude Code process. This is a code-execution path for any command Claude Code is asked to run.

**No fix is present.** The only safe approach is to have Claude Code write `TOOL_INPUT_COMMAND` as an environment variable and have the script read it from `$ENV_VAR`, never interpolated into the command string. Or the hooks.json would need to use a mechanism that passes the value out-of-band (e.g., a temp file or stdin), not as a shell-expanded argument.

### 2. Newlines in `TOOL_INPUT_COMMAND` break `echo "$COMMAND" | grep` matching in all three scripts

**Files:** `guard-direct-dotfile-edit.sh` lines 34, 36; `remind-chezmoi-commit.sh` lines 14, 19; `guard-install.sh` lines 34, 36, 50

All three scripts pass `COMMAND` through `echo "$COMMAND" | grep -qE`. When `TOOL_INPUT_COMMAND` contains newlines (e.g., a multi-line bash command passed as one string), `echo` will emit multiple lines. The grep then matches against each line independently.

**Effect on guard-direct-dotfile-edit.sh:** The bypass check on line 36 anchors with `^`:
```bash
echo "$COMMAND" | grep -qE '^(chezmoi (edit|cd|add|source-path)|.*\.local/share/chezmoi)'
```
If the command string is:
```
chezmoi edit ~/.zshrc
vim ~/.bashrc
```
Line 1 matches the `^chezmoi` bypass pattern, so `exit 0` fires — the block on line 2 (`vim ~/.bashrc`) is never evaluated. An adversarial multi-line command can bypass the entire guard by prepending any `chezmoi` command on the first line.

**Effect on remind-chezmoi-commit.sh:** The dry-run skip on line 19 uses `grep -q '\-\-dry-run'` across all lines, which is correct. But the trigger on line 14 `chezmoi (apply|re-add|add)` would match any line in a multi-line command, potentially triggering the reminder for commands that only mention chezmoi incidentally in a comment.

**Effect on guard-install.sh:** Same bypass possibility — a multi-line command could have `pip install -e .` on line 1 and `pip install --user maliciousbag` on line 2. The `pip install -e` allow-through fires on the first line before the blocked pattern is checked for the second.

### 3. `^` anchor in chezmoi guard does not anchor to command start, only to line start

**File:** `guard-direct-dotfile-edit.sh` line 36

```bash
echo "$COMMAND" | grep -qE '^(chezmoi (edit|cd|add|source-path)|.*\.local/share/chezmoi)'
```

The intent is "the command begins with a chezmoi invocation." But with multi-line input (see finding 2), `^` anchors to the start of each line. A command such as:
```
# chezmoi add
vim ~/.bashrc
```
Has line 1 starting with `# chezmoi add`. The pattern `.*\.local/share/chezmoi` would not match. But `chezmoi add` appearing anywhere as a full first word on any line would match `^chezmoi`. A comment or heredoc that begins a line with the word `chezmoi` would trigger the bypass.

Even without newlines: the pattern `.*\.local/share/chezmoi` starts with `.*`, meaning it matches anywhere in the string (the `^` is cancelled by `.*` prefixing the second alternative). Any command that contains `.local/share/chezmoi` anywhere in it — including as an argument in a completely unrelated command like `ls ~/.local/share/chezmoi` — bypasses the guard entirely.

## P2 IMPORTANT

### 4. `CLAUDE_PLUGIN_ROOT` is not a documented Claude Code variable — its behavior is unverified

**Files:** Both `hooks.json` files, line 9

Both hooks reference `${CLAUDE_PLUGIN_ROOT}` to locate scripts:
```json
"command": "bash ${CLAUDE_PLUGIN_ROOT}/hooks/scripts/guard-install.sh ..."
```

Claude Code's documented hook variables (from published SDK docs as of the knowledge cutoff) are environment variables passed to hook processes, not variables that are interpolated into the `command` string itself. The documented variables for hook event data are things like `CLAUDE_TOOL_NAME`, `CLAUDE_TOOL_INPUT`, etc., delivered as environment variables to the spawned process.

`CLAUDE_PLUGIN_ROOT` has no documented basis in the Claude Code hooks specification. If Claude Code evaluates the `command` string with variable expansion and `CLAUDE_PLUGIN_ROOT` is not set in that environment, the expansion produces an empty string, and the hook command becomes:
```bash
bash /hooks/scripts/guard-install.sh "..."
```
This resolves to a path from the filesystem root, fails silently (path does not exist), and the guard never fires. Claude Code's behavior on a non-zero hook exit versus a command-not-found error may differ — if it treats the hook as "passed" on any failure, all guards are silently disabled.

**This is the most operationally dangerous finding:** if `CLAUDE_PLUGIN_ROOT` is undefined in the hook execution environment, every guard is a no-op.

### 5. `TOOL_INPUT_COMMAND` variable interpolation timing — expanded by Claude Code before shell, not by shell

**Files:** Both `hooks.json` files, line 9

Closely related to finding 1. The JSON `command` value is a string template. If Claude Code performs its own variable substitution (replacing `${TOOL_INPUT_COMMAND}` before passing the result to the shell), then the shell receives the already-expanded value — which may contain shell metacharacters. This is the standard path for shell injection via template expansion.

If instead Claude Code passes the `command` string as-is to `bash -c` and sets `TOOL_INPUT_COMMAND` as an environment variable for the child process, the injection risk from finding 1 does not apply. The hooks.json syntax `\"${TOOL_INPUT_COMMAND}\"` strongly suggests template-style substitution (Claude Code fills in the value before the shell sees it), which means the injection is real.

The correct pattern would be:
```json

```
...with the script reading `TOOL_INPUT_COMMAND` from its environment directly, never as a CLI argument.

### 7. `guard-install.sh` pip allow-through fires before all blocked patterns are checked

**File:** `guard-install.sh` lines 33–46

```bash
for pattern in "${BLOCKED_PATTERNS[@]}"; do
  if echo "$COMMAND" | grep -qiE "$pattern"; then
    # Allow editable local packages (pip install -e .)
    if echo "$COMMAND" | grep -qiE '\bpip install -e\b'; then
      exit 0
    fi
    ...
    exit 1
  fi
done
```

The `pip install -e` allow-through is checked inside the loop, after any blocked pattern matches. If the command is `npm install -g foo`, the inner `pip install -e` check also runs — it fails (correctly), and `exit 1` fires. But the logic is fragile: if someone constructs:
```
npm install -g foo && pip install -e .
```
The outer grep matches `npm install -g`, the inner grep matches `pip install -e .`, and `exit 0` fires — the `npm install -g` is allowed through because the command also contains `pip install -e .`.

The correct fix is to check the allow-through only when the matched pattern is pip-related, not for every blocked pattern.

## P3 NICE-TO-HAVE (functional correctness issues, not style)

### 10. Regex pattern `'echo.*>>.*~/\.'` in chezmoi guard uses `.*` which crosses line boundaries mentally

**File:** `guard-direct-dotfile-edit.sh` line 24

Pattern: `'echo.*>>.*~/\.'`

This is intended to catch `echo "foo" >> ~/.zshrc`. However, `.*` in ERE is greedy and matches any characters including `>` itself, meaning this pattern would also match:
```bash
echo "backup>>done" > ~/not-a-dotfile
```
Because `.*>>.*~/\.` matches `backup>>done" > ~/not-a-dotfile` if the `~/\.` occurs after a second `>`. This is an overmatch that produces false positives. Minor in practice but incorrect.

### 11. `cp .* ~/\.` and `mv .* ~/\.` patterns have unescaped `.` in source position

**File:** `guard-direct-dotfile-edit.sh` lines 29–30

```
'cp .* ~/\.'
'mv .* ~/\.'
```

The `\.` at the end correctly escapes the dot in `~/.<filename>`. But the `.*` in the middle matches any characters. More importantly, `cp` without a space after it would also match `cprog ~/something/.hidden` if the regex engine allowed it — but actually the leading `cp ` (with space) is not in the pattern. The pattern is `cp .* ~/\.` — `cp` is literal, then a space, then `.*`. This is fine for basic cases. Not a bug.

## Root Cause Pattern

Findings 1, 2, 3, 4, and 5 share the same root cause: **the hooks receive untrusted input (TOOL_INPUT_COMMAND) as a shell-interpolated argument rather than as an environment variable read inside the script.** The entire trust model is wrong at the architecture level. The fix is not to patch individual patterns — it is to change both hooks.json files to pass no arguments and have each script read `TOOL_INPUT_COMMAND` directly from its environment:

```json
"command": "bash ${CLAUDE_PLUGIN_ROOT}/hooks/scripts/guard-install.sh"
```
```bash
COMMAND="${TOOL_INPUT_COMMAND:-}"
```

This eliminates the shell injection surface entirely and makes multi-line handling controllable within the script using proper read/mapfile techniques.
