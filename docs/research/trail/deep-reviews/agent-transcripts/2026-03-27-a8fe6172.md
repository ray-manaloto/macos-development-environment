### Issues

**Important (should fix)**

1. **Missing error-path tests.** The test suite only covers happy paths. There are no tests for:
   - `doppler_list_secrets` returning `{}` when `returncode != 0`
   - `doppler_get_secret` returning `None` when `returncode != 0`
   - `doppler_set_secrets` returning a nonzero exit code on failure
   - `doppler_list_secrets` handling malformed JSON (would raise `json.JSONDecodeError`)

   The plan itself did not spec these, but the plan is a minimum -- the wrapper has real error-handling branches that are currently untested. This matters because Task 4 (sync) and Task 5 (validate) will depend on these functions behaving correctly on failure. If a future refactor breaks the error path, there will be no regression signal.

2. **No `json.JSONDecodeError` handling in `doppler_list_secrets`.** If the Doppler CLI returns a 0 exit code but garbled output, `json.loads(result.stdout)` will raise an unhandled `JSONDecodeError`. The `doppler_get_secret` and `doppler_set_secrets` functions are resilient to bad output, but `doppler_list_secrets` is not. Consider wrapping the parse in a try/except that logs and returns `{}`.

3. **`doppler_get_secret` does not log on failure.** Both `doppler_list_secrets` and `doppler_set_secrets` call `logger.bind(...).error(...)` on failure, but `doppler_get_secret` silently returns `None`. For consistency and debuggability, it should log the stderr too. The downstream `sync.py` and `validate.py` modules will call this function heavily, and silent failures will make debugging difficult.

**Suggestions (nice to have)**

4. **`doppler_set_secrets` is vulnerable to values containing `=`.** The pair formatting `f"{k}={v}"` will produce `KEY=val=ue` if a secret value contains `=`. Doppler CLI interprets this correctly (splits on the first `=`), so this is not a bug today, but it is worth a comment or docstring note to document the assumption explicitly.

5. **`patch("subprocess.run")` targets the global, not the module-local reference.** The tests patch `subprocess.run` at the global level rather than `mde.secrets.doppler.subprocess.run`. This works because the module uses `subprocess.run` directly, but it is fragile -- if a future import rearranges things or another test in the same process patches differently, these could collide. The more precise patch target `"mde.secrets.doppler.subprocess.run"` is safer. Similarly, `patch("shutil.which")` should be `"mde.secrets.doppler.shutil.which"`.

6. **`doppler_set_secrets` test does not verify the `KEY=VALUE` pairs are in the args.** The test asserts that `"doppler"`, `"secrets"`, and `"set"` appear in the command but does not check that `"KEY1=val1"` and `"KEY2=val2"` are present. This means a regression that drops the actual secret pairs would not be caught.

7. **`check=False` is implicit.** The `subprocess.run` calls rely on the default `check=False` behavior. An explicit `check=False` would make the intent clearer, since the code explicitly handles `returncode != 0`.
