### CRITICAL

**1. `hooks/hooks.json` + `hooks/scripts/guard-install.sh`: Wrong environment variable for Bash tool command**

The hook passes `"${TOOL_INPUT}"` as `$1` to the shell script, but the correct Claude Code plugin hook variable for the Bash tool's `command` field is `${TOOL_INPUT_COMMAND}`. The variable `${TOOL_INPUT}` is not a defined env var in the hook execution context; only `${TOOL_INPUT_<FIELDNAME>}` variants are expanded by the Claude Code runtime.

From the marketplace's hooks reference (`plugin-master/skills/advanced-features-2025/references/hooks-advanced.md`):
```
${TOOL_INPUT_COMMAND}   — Command (Bash tool)
${TOOL_INPUT_FILE_PATH} — File path (Write/Edit tools)
```

As written, `$1` in `guard-install.sh` will always be an empty string (or the literal text `${TOOL_INPUT}` depending on shell quoting), meaning the hook silently passes every command through without ever blocking anything. This is the opposite of a safety net — it looks like it works but does nothing.

Fix:
```json
"command": "bash ${CLAUDE_PLUGIN_ROOT}/hooks/scripts/guard-install.sh \"${TOOL_INPUT_COMMAND}\""
```

Note: the `chezmoi-toolkit` plugin has the identical bug. Both need the same fix.

**2. `hooks/scripts/guard-install.sh`: Exception logic only fires after the outer match, breaking `pip install -e` passthrough**

The `pip install -e` exception is inside the loop body but is only reached after the outer `grep -qi "$pattern"` matches. The blocked patterns list includes both `'pip install --user'` and `'pip install -g'`. However, `pip install -e .` does not match either of those patterns, so the exception branch at line 35 is unreachable for those two patterns — it can only be reached if a future pattern like `pip install` (no flags) were added.

More dangerously: `pip install -g` is not a real pip flag. `pip` has no `-g` flag. This pattern will never match any real command. Its presence in the blocked list misleads readers into thinking pip global installs are covered, while the actually dangerous pattern (`pip install <package>` with no `-e`) is absent. The production Python hook in `src/mde/hooks/guard_install.py` correctly uses `\bpip\s+install\b(?!.*(?:-e\s*\.|\.))` — a negative lookahead — to catch this case. The shell script's approach is both inaccurate and redundant.

### WARNING

**3. `hooks/scripts/guard-install.sh`: `direnv` block is too aggressive**

Lines 49–54 block any command that contains the string `direnv`. This will block `mise direnv activate`, `mise direnv exec`, or even reading files that mention direnv (`cat .envrc.bak | grep direnv`). The intent is presumably to block `direnv allow` or `eval "$(direnv hook bash)"`, but the pattern matches on the bare word. This will produce false positives that confuse users trying to document or migrate away from direnv.

A tighter pattern would be `direnv\s+(allow|hook|exec)`.

**4. `hooks/scripts/guard-install.sh`: `gem install` pattern can match `mise install --gem` or similar**

The pattern `gem install` (substring match via `grep -qi`) will match any command containing those two words in sequence, including `mise install --gem-flag` or a comment like `# previously: gem install bundler`. The production Python hook uses word-boundary regexes (`\bpipx\s+install\b`) to avoid this. The shell script should use `grep -qiw` or anchor to word boundaries: `grep -qiE '\bgem install\b'`.
