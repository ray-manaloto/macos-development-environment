## Security Review: chezmoi-toolkit and mise-toolkit plugins

---

### CRITICAL

**C1 — Command injection via unquoted `${TOOL_INPUT_COMMAND}` expansion in hooks.json**

`chezmoi-toolkit/hooks/hooks.json:9`, `hooks.json:21`, `mise-toolkit/hooks/hooks.json:9`

All three hook invocations take the form:

```json
"command": "bash .../guard-direct-dotfile-edit.sh \"${TOOL_INPUT_COMMAND}\""
```

The variable `${TOOL_INPUT_COMMAND}` is expanded by the shell that evaluates the JSON `command` string before it is passed to `bash`. If the hook runner performs naive word-splitting on the resulting string, or if any intermediate shell (e.g. `sh -c "..."`) is used to evaluate it, a command string containing `"` characters can terminate the quoted argument and inject arbitrary shell commands.

Concretely, if `TOOL_INPUT_COMMAND` contains `"; rm -rf ~; echo "`, the final command string becomes:

```
bash guard-direct-dotfile-edit.sh "" ; rm -rf ~ ; echo ""
```

The risk depends on exactly how Claude Code's plugin hook runner evaluates the `command` field. If it passes the field through `sh -c` (common for hook runners that don't exec directly), this is exploitable by any bash command that Claude decides to run — meaning the hook designed to restrict Claude's behavior can be turned against the user. This needs to be verified against the Claude Code hook runner specification and hardened.

**Mitigation:** Pass the command via a safe mechanism that does not involve shell interpolation — e.g. a wrapper that reads the command from `stdin` or an environment variable rather than a positional argument embedded in a JSON string. If positional arguments must be used, the plugin runner must exec the script directly (not via `sh -c`), and `TOOL_INPUT_COMMAND` must be validated as safe before substitution.

### WARNING

**W1 — `grep -E` pattern used against attacker-controlled input without anchoring — guard bypass is possible**

`guard-direct-dotfile-edit.sh:34`, `remind-chezmoi-commit.sh:14`, `guard-install.sh:34`

The guard logic pipes `$COMMAND` into `grep -qE "$pattern"` to detect forbidden operations. The patterns are fixed strings, which is fine. However, the allow-list bypass check in `guard-direct-dotfile-edit.sh` is the real concern:

```bash
if echo "$COMMAND" | grep -qE '(\.local/share/chezmoi|chezmoi source-path|chezmoi cd|chezmoi edit)'; then
  exit 0
fi
```

A command like:

```bash
vim ~/.zshrc  # chezmoi edit workaround
```

contains the substring `chezmoi edit` in a comment, which makes `grep` match and causes `exit 0` — the block is bypassed. Similarly:

```bash
echo "chezmoi cd" >> ~/.bashrc
```

would match the allowlist before the blocklist triggers. The allowlist check runs after the blocklist match has already fired, which is the correct order, but the substring match on the allowlist means any comment or string argument containing the allowlist keywords bypasses the guard entirely.

**Mitigation:** Check for the allowlist keywords only at the start of the command (anchor with `^`) or match full word boundaries, and strip comments before matching.

**W2 — `remind-chezmoi-commit.sh` changes the working directory with `cd` inside an `if` condition**

`remind-chezmoi-commit.sh:30`

```bash
if cd "$SOURCE_DIR" && git status --porcelain 2>/dev/null | grep -q .; then
```

The `cd "$SOURCE_DIR"` runs in the script's process, so after this line completes the working directory of the script is changed to `$SOURCE_DIR`. While this has no security impact in itself (the script exits immediately after), if this script is ever extended with code after the `if` block, that code will execute in the chezmoi source directory rather than the original working directory — a silent, unexpected side-effect. The `set -euo pipefail` at the top means a `cd` failure aborts, which is correct, but the cwd mutation is still a footgun.

**Mitigation:** Use a subshell: `if (cd "$SOURCE_DIR" && git status ...)`.

**I1 — `guard-install.sh` pip allowlist check fires on wrong branch**

`guard-install.sh:36-38`

```bash
if echo "$COMMAND" | grep -qiE '\bpip install -e\b'; then
  exit 0
fi
```

This check runs only inside the `for pattern in "${BLOCKED_PATTERNS[@]}"` loop. The `pip install --user` pattern is in `BLOCKED_PATTERNS`, but `pip install -e .` does not match `\bpip install --user\b`, so the allowlist check for `-e` would never be reached via that specific pattern anyway. The allowlist is in the right place logically but is dead code for the `pip install --user` pattern specifically — it would only be reached if a future pattern matched `pip install -e`. No functional bug today, but it's confusing and could cause a future regression if patterns change.
