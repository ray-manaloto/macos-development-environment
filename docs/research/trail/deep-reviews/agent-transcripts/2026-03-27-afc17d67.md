Based on my comprehensive research of the official Claude Code documentation, here are the complete answers to your questions about prompt-type hooks:

## 1. Is there a field/flag to force JSON output from prompt hooks?

**NO**. There is no `outputFormat`, `responseFormat`, `json`, or similar field. The JSON response format is **hardcoded and non-configurable**. Claude Code simply expects the model to return valid JSON—if it doesn't, the response is treated as invalid.

## 2. Exact JSON Schema for Prompt Hook Responses

```json
{
  "decision": "yes" | "no",
  "reasoning": "optional explanation"
}
```

**Required:**
- `decision` — exactly `"yes"` or `"no"` (string, case-sensitive)

**Optional:**
- `reasoning` — string explaining the decision (recommended for audit trails)

Any other field names (like `ok`, `allow`, `approved`) will cause validation to fail.

## 3. What Causes "JSON Validation Failed" Errors

The error occurs when:
1. **Missing `decision` field** — the response JSON doesn't have a `decision` key
2. **Invalid `decision` value** — the value isn't exactly `"yes"` or `"no"` (e.g., `true`, `1`, `"Yes"`, `"ok"`)
3. **Malformed JSON** — the response isn't valid JSON syntax
4. **Empty response** — model returns nothing or whitespace

**Most common cause**: Your prompt instructs the model to return `{"ok": true}` or `{"ok": false}` instead of `{"decision": "yes"/"no"}`.

## 4. Configuration Options for Response Parsing

**NONE**. There are **no configuration options** to control how responses are parsed or validated. The schema is hardcoded into Claude Code.

## 5. Complete Hook Field Schema

**All possible fields for a prompt-type hook entry:**

| Field | Required | Type | Description |
|-------|----------|------|-------------|
| `type` | yes | string | Must be `"prompt"` |
| `prompt` | yes | string | Text sent to model; supports `$ARGUMENTS` placeholder for hook input JSON |
| `model` | no | string | Model ID (default: fast model). Example: `"claude-opus-4-1-20250805"` |
| `timeout` | no | number | Seconds before canceling (default: 30 seconds) |

**That's it.** No schema/validation fields, no output format controls, no response type indicators.

## Complete Example

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "prompt",
            "prompt": "Analyze this shell command for security risks:\n\n$ARGUMENTS\n\nIs it safe to execute? Respond with {\"decision\": \"yes\"} or {\"decision\": \"no\"}, optionally with a \"reasoning\" field.",
            "model": "claude-opus-4-1-20250805",
            "timeout": 30
          }
        ]
      }
    ]
  }
}
```

**Valid model responses:**
```json
{"decision": "yes", "reasoning": "Safe npm test command"}
{"decision": "no", "reasoning": "Uses rm -rf destructively"}
```

## Key Implementation Notes

- **No validation control**: If your prompt doesn't clearly instruct the model to use the `decision` field, the response will fail validation
- **Non-blocking on failure**: Invalid JSON is treated as a soft error—execution continues as if the hook didn't fire
- **$ARGUMENTS substitution**: Replace with hook input JSON formatted as a string—you can reference any field from the event's input schema
- **Decision blocking**: `"no"` is converted to the appropriate block action per event type (`PreToolUse` → `permissionDecision: "deny"`, `Stop` → `decision: "block"`, etc.)
